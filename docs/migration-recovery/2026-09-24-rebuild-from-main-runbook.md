## الإجراء

### ١) مشروعٌ جديد
أنشئ مشروعَ Supabase، وخُذ منه: `PROJECT_REF` · كلمةَ مرور القاعدة ·
مفتاحَ الخدمة. ولا تُعِد استعمالَ اعتمادِ الإنتاج.

### ٢) مضيفُ المجمِّع لا يُخمَّن
ليس واحداً لكلّ المشاريع ولو اتّحد الإقليم، ولا تُرجعه واجهةُ
الإدارة. جرِّب المرشّحين حتى يردّ أحدُهم:

```bash
for h in aws-0-<region>.pooler.supabase.com aws-1-<region>.pooler.supabase.com; do
  psql "postgresql://postgres.$REF@$h:5432/postgres" -c "select 1" && echo "$h" && break
done
```

> والاتصالُ المباشر `db.<ref>.supabase.co` لا يصلح من مُشغِّلات
> GitHub: عنوانُه IPv6 وهي IPv4.

### ٣) الترحيلات
```bash
npm run supabase -- db push --db-url "$DB_URL" --include-all
```
ثمّ تحقّق: ٥١ صفاً، والأحدث `20260924140000`، وصفرُ معلَّق عبر
`supabase/verification/assert-ledger-correspondence.py`.

### ٤) البيانات
```bash
psql "$URL" -f supabase/scripts/seed_test_seasons.sql      # بيئةُ اختبار فقط
```
وللاستعادةِ الحقيقية: استرجع نسخةَ البيانات بدل هذا السطر.

### ٥) أوّلُ مدير — **يلزم Node 22 أو أحدث**
```bash
SUPABASE_URL=… SUPABASE_SERVICE_ROLE_KEY=… ADMIN_EMAIL=… ADMIN_PASSWORD=… ADMIN_NAME=… \
  node supabase/scripts/seed_first_admin.mjs
```

أبقِ المجرى مفتوحاً (`yes 'نعم' | node …`) — فـ`printf` يُغلقه فتُغلق
`readline` قبل السؤال.

## ثلاثةُ مطبّاتٍ رُصدت بالتجربة

**١. `@supabase/supabase-js` يحتاج Node ≥ 22.** `createClient` يبني
عميلَ Realtime دائماً، وهو يتطلّب WebSocket أصليّاً لا يوجد في Node 20.
والاستيرادُ وحدَه ينجح — الإخفاقُ عند بناء العميل.

**٢. سياساتُ التخزين تنجو من هدم `public`.** تعيش في schema `storage`،
وترحيلةُ الأساس تُنشئها بـ`create policy` بلا `if not exists`. فعلى
مشروعٍ **جديد** لا إشكال؛ وعلى مشروعٍ أُعيد بناؤه سابقاً تتوقّف الدفعةُ
عند الترحيلة ٤٧. تُمسح أوّلاً إن كان المشروعُ مُعاداً.

**٣. التخزينُ لا يُمسح بـ SQL.** `storage.protect_delete()` ترفض
الحذفَ المباشر وتُحيل إلى الواجهة — وهي محقّة: حذفُ الصفّ دون الكائن
يترك يتيماً.

## ما لم يُثبَت بعد — ولا يُقرأ سكوتٌ عنه إثباتاً

**الخطواتُ المتبقيةُ من المرحلة أ (أ٦–أ١٠) والمرحلةُ ب كلُّها موقوفةٌ
على اعتمادٍ لا نملكه**: رمزُ الوصول (`SUPABASE_ACCESS_TOKEN`) مقصورٌ
على مشروع الإنتاج، فيردّ ٤٠٣ على مشروع التمرين:

```
unexpected list functions status 403:
  "Your account does not have the necessary privileges to access this endpoint"
```

والدليلُ على أنّ السببَ نطاقُ الرمز لا صلاحيةُ الحساب: **الرمزُ نفسُه
نشر `send-pilgrim-push` على الإنتاج بنجاح** في التشغيل
[35999285337](https://github.com/aeltorgoman/alaqsa-hajj/actions/runs/35999285337).

فما يبقى بلا إثبات:

- أ٨ — فتحُ مستندٍ من طرفٍ إلى طرف عبر `pilgrim-doc`
- أ٩/أ١٠ — دخولُ الموظّف وجلسةُ البوابة عبر الدوالّ المنشورة
- **ب٣ — إقفالُ الموسم عبر `season-admin`** كما يفعل التطبيق

ولم يُستبدَل بنداءٍ مباشرٍ لـ`close_season()`: الغرضُ اختبارُ المسار
الحقيقيّ، واختصارُه يُفرغ التمرينَ من معناه.

**المطلوبُ لإكماله:** رمزُ وصولٍ يشمل مشروعَ التمرين، يُحفظ سرّاً
منفصلاً (`TMP_ACCESS_TOKEN`). ولا شيءَ غيرُه.
