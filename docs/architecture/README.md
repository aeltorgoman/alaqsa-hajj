# معمارية نظام الأقصى — نقطة الدخول

هذا المجلد هو **الذاكرة المعمارية للمشروع**. كل قرار بُني عليه النظام مكتوبٌ هنا بنصّه الذي اعتُمد، لا بملخّص له.

> **الوثائق هنا مرجعٌ مُلزِم لا أرشيف.** ما يخالفها في الشيفرة **عيبٌ يُصلَح**، لا أمرٌ واقع يُبرَّر.

## ١. سلّم المرجعية — أيّ وثيقة تحكم أيّ مجال

```
Engineering Playbook            المرجع الهندسي العام للمشروع كله
        │
        ├── Security Architecture      ← السلطة العليا في الأمن
        │        │
        │        ├── S1 Implementation Design   الهوية والأساس
        │        ├── S2 Implementation Design   الدخول وإدارة المستخدمين
        │        ├── S3 Implementation Design   التفويض ودوال Edge
        │        └── S4 Implementation Design   RLS وسحب صلاحيات anon
        │
        ├── B0 Implementation Design   الإقلاع والتهيئة (مسار منتج)
        │
        └── Season Architecture         المواسم وثوابتها (خارج هذا المجلد)
```

**Security Architecture هي السلطة العليا في كل ما يمسّ الأمن.** ووثائق التنفيذ (S1–S4 و B0) **لا تنافسها ولا تعدّلها**: كلٌّ منها يشرح **كيف** نفّذت مرحلةٌ بعينها ما تفرضه المعمارية، ويحمل قرارات تنفيذ محدودة النطاق.

**عند أي تعارض، المعمارية تسبق التنفيذ.** وإن كشف التنفيذ خطأً في المعمارية، **تُعدَّل المعمارية بإصدار جديد ومراجعة** — لا يُتجاوز نصّها صمتاً.

## ٢. خارطة التنفيذ — عشر مراحل بترتيب مُلزِم

| # | المرحلة | الحالة |
|---|---|---|
| **س٠** | احتواء عاجل — `Scan-passport` · إغلاق التسجيل الذاتي | 🟢 تطوير مكتمل |
| **س١** | الأساس — `user_profiles` · `has_permission()` | 🟢 مكتملة ومنشورة |
| **س٢** | الدخول — `signInWithPassword` · `user-admin` | 🟢 تطوير مكتمل |
| **س٣** | التفويض — النمط الثلاثي على دوال Edge الثلاث | 🟢 مكتملة ومنشورة |
| **س٤** | **RLS وسحب صلاحيات `anon`** | 🟡 تطوير مكتمل · النشر موقوف على شروطه |
| **س٥** | حذف الشيفرة المعيبة — `verify_user` · `public.users` | ⬜ |
| **س٦** | التخزين ومستندات البوابة معاً | ⬜ |
| **س٧** | البوابة — رمز جلسة وحدّ محاولات | ⬜ |
| **س٨** | التدقيق — `audit_log` | ⬜ |
| **س٩** | إنهاء — حدّ معدّل · تدوير الأسرار | ⬜ |

**ومسار المنتج — منفصل:**

| # | المرحلة | يعتمد على | الحالة |
|---|---|---|---|
| **ب٠** | **الإقلاع والتهيئة** — Bootstrap Wizard · تذكرة الإقلاع | س٤ (شرط تقنيّ) | ⬜ تصميم معتمد |

**ولماذا ب٠ منفصلة رغم اعتمادها على س٤:** الإقلاع **ميزة منتج** لا مرحلة أمنية، ومسار الأمن يبقى أمناً خالصاً. والتبعية تقنية أحادية الاتجاه: قبل س٤ لا معنى لحارس الإقلاع أصلاً، **وس٤ لا تحتاج ب٠ إطلاقاً**.

**الترتيب ليس اقتراحاً.** §١٤ من المعمارية تشرح سبب كل تبعية، وأهمّها:

- **س٤ بعد س٣** — سحب صلاحيات `anon` قبل أن يحمل التطبيق JWT حقيقياً = توقّف كامل.
- **س٥ بعد س٤** — حذف مسار الدخول القديم قبل عمل الجديد يقطع الدخول.
- **س٦ غير قابلة للتقسيم** — إغلاق حاوية المستندات بلا روابط موقّعة يكسر بوابة الحاج.

## ٣. مسار العمل المُلزِم لكل مرحلة

```
تصميم → اعتماد → تنفيذ → PR → مراجعة مستقلة → اعتماد → دمج → نشر → تحقّق
```

**ولا يُتجاوز هذا التسلسل إلا بموافقة صريحة استثنائية.**

وكل مرحلة تفصل **اكتمال التطوير** عن **اكتمال النشر**: تُعتبر المرحلة مكتملة تطويراً حين تُدمج شيفرتها وتُراجَع، ومهامّ النشر تُتابَع في سجلّ مستقلّ (§١٤.١ من المعمارية) ولا تعطّل المرحلة التالية ما لم تكن تبعية تقنية فعلية.

## ٤. القواعد الدائمة — تسري على كل ما يُبنى بعد س٤

مصدرها `S4_IMPLEMENTATION_DESIGN.md` §٩.٢، ومعها قاعدة دوال Edge من §٧.٢ من المعمارية:

| # | القاعدة |
|---|---|
| **ق١** | **الجداول الجديدة لا ترث صلاحيات `anon` إطلاقاً** — الامتيازات الافتراضية مسحوبة عن `anon` كجزء دائم من الأساس |
| **ق٢** | **كل Edge Function جديدة تستعمل `authorize()` المشتركة** — لا دالة تكتب منطق تفويض بنفسها |
| **ق٣** | **كل مدخل مجهول جديد يُضاف إلى جرد الوصول المجهول قبل النشر** — والجرد هو المصدر الوحيد للحقيقة، وما ليس فيه **عيبٌ معماري** |
| **ق٤** | **الملفات المولَّدة لا تتلقّى تعديلاً يدوياً دائماً** — التعديل مؤقّت ويُسجَّل بـTODO لحظة إدخاله |
| **ق٥** | **النمط الثلاثي مُلزِم** لكل دالة Edge محميّة: `verify_jwt` + `getUser(jwt)` + `has_permission()` — **الثلاثة معاً** |
| **ق٦** | **نمط الإقلاع** (§٧.٢) مسموح **لدالة واحدة في النظام كله**. وأي دالة أخرى بـ`verify_jwt = false` **عيبٌ معماري** |
| **ق٧** | **مسار الإقلاع لا يعرف المورّد** (الثابت أ١١) — لا فحص يميّز مورّداً عن عميل |

## ٥. كيف تُقرأ هذه الوثائق

- **لفهم «لماذا» قرارٍ ما:** ابدأ بـ `SECURITY_ARCHITECTURE.md` — كل قسم فيه يذكر البدائل المرفوضة وسبب رفضها.
- **لفهم «كيف» نُفِّذت مرحلة:** اقرأ وثيقة تنفيذها؛ فيها النطاق وما لا يشمله، والمخاطر، وخطة التحقّق، وخطة التراجع.
- **قبل إضافة ميزة تمسّ البيانات:** اقرأ §٤ من `S4_IMPLEMENTATION_DESIGN.md` (جرد الوصول المجهول) و§٩.٢ (قواعد الأساس).

**وما رُصد ولم يُبنَ يعيش في `BACKLOG.md`** — لا في تعليقات متفرّقة ولا في ذاكرة أحد. وقاعدته: ما يمنع التنفيذ أو يكسر الأمن أو المعمارية **يوقف العمل ويُبلَّغ**، وما دون ذلك **يُسجَّل ويُكمَل التنفيذ**.

**كل وثيقة تحمل سجلّ إصدارات في آخرها.** والإصدار المحفوظ هنا هو **آخر إصدار معتمد** وقت إضافته إلى المستودع؛ وأي تعديل لاحق يمرّ بمراجعة كأي تغيير في الشيفرة.

## ٦. تطوّر المعمارية — Architecture Evolution

**هذه وثائق حيّة لا نصوص محنَّطة.** المشروع ينمو، والمعمارية تنمو معه — لكن نموّها محكوم بقواعد، وإلا فقدت صفتها مرجعاً.

### القواعد

| # | القاعدة |
|---|---|
| **ط١** | **كل تغيير معماري يُنشئ إصداراً جديداً من الوثيقة.** لا يُعدَّل نصٌّ معتمد في مكانه |
| **ط٢** | **كل إصدار يحفظ تاريخ القرارات السابقة.** سجلّ الإصدارات في آخر كل وثيقة جزءٌ منها، ولا يُختصر ولا يُحذف منه شيء |
| **ط٣** | **لا يُستبدل قرار معماري معتمد صمتاً.** الاستبدال يُذكر صراحةً: ما الذي تغيّر، ولماذا، وما الذي ألغاه |
| **ط٤** | **أي تغيير في Security Architecture يستوجب مراجعة معمارية صريحة.** لا يمرّ ضمن PR تنفيذيّ ولا بوصفه تفصيلاً جانبياً |
| **ط٥** | **وثائق التنفيذ تصف كيف تُنفَّذ المعمارية، لا كيف تُعرَّف.** لا تملك تعديل قرار معماري، وإنما تكشف الحاجة إليه فيُحسم في المعمارية نفسها |

### لماذا هذه القواعد بالذات

**تاريخ القرار جزء من قيمته.** قرارٌ نعرف بدائله المرفوضة وسبب رفضها يُبنى عليه بثقة؛ وقرارٌ بلا تاريخ يُعاد فتحه كل مرة، أو — وهو أسوأ — يُنقض بلا أن ينتبه أحد.

**الأثر العملي:** إن اقتضى التنفيذ ما يخالف المعمارية، **يتوقّف ويُرفَع التعارض** — لا يُنفَّذ المخالف ويُوثَّق بعده. وهذا ما وقع فعلاً في س٣ و س٤: كُشف تعارضان أثناء التصميم، فحُسما في وثيقة المعمارية وقراراتها قبل كتابة سطر واحد.

### الشكل العملي للتغيير

```
اكتشاف الحاجة  →  توصيف التعارض  →  إصدار جديد من الوثيقة
      →  مراجعة معمارية صريحة  →  اعتماد  →  ثم التنفيذ
```

وسجلّ الإصدارات يُظهر السلسلة كاملة. مثال قائم في هذا المجلد: `SECURITY_ARCHITECTURE.md` مرّت بـ **v1.0 → v1.1 → v1.2 → v1.3 → v1.4**، وكل إصدار يذكر ما غيّره وما لم يمسّه — **ولا واحد منها حذف قرار سابقه، بل نسخه صراحةً**.
