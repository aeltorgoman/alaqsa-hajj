# ٣. Technical Design

## ٣.١ الحالة القائمة — جرد كامل من الإنتاج

**١٤ جدولاً تمنح `anon` سبع صلاحيات كاملة** (`SELECT,INSERT,UPDATE,DELETE,REFERENCES,TRIGGER,TRUNCATE`) بسياسة `using (true)` واحدة:

```
announcements · buses · camps · custom_charges · financial_group_members
financial_groups · flights · notification_deliveries · passengers
payments · pricing_settings · rooms · seasons · users
```

**نظيفة سلفاً — لا تُمسّ:**

| الجدول | الحالة | مصدرها |
|---|---|---|
| `user_profiles` | ٤ سياسات · صفر منح لـ`anon` | س١ |
| `company_config` | سياستان · صفر منح لـ`anon` | مزامنة النشر |
| `company_assets` | ٥ سياسات · `SELECT` لمفاتيح محدَّدة | مزامنة النشر |
| `pilgrim_push_subscriptions` | `service_role` فقط | قائم |

## ٣.٢ القرار الحاسم — القراءة تُفصل عن الكتابة

§٦.٤ تقول «صلاحية مطابقة لبند `NAV`». **تطبيقها حرفياً على القراءة يوقف النظام** — والدليل من الشيفرة لا من التقدير:

`App.tsx` يجلب **كل الحجاج مرة واحدة عند الدخول** لأي مستخدم مهما كانت صلاحياته، ويمرّرهم إلى ثماني صفحات (مصدر الحقيقة الواحد). و`passengersLoading` يحجب **كل** الصفحات حتى يكتمل.

فلو اشترطت سياسة `select` على `passengers` صلاحية `manage_passengers`:

> **موظّف الحسابات** (`manage_payments` وحدها) يدخل، فيصله **صفر حاج**، فتُعرض صفحة الحسابات فارغة تماماً — بلا خطأ ولا تفسير. ومثله موظّف التقارير وموظّف الباصات.

**القرار المقترح:**

```
SELECT   →  لكل موظّف نشط        (is_active)
INSERT · UPDATE · DELETE  →  الصلاحية المطابقة لبند NAV
```

**لماذا هذا ليس تراخياً:** الخطر الذي تغلقه س٤ هو **مفتاح النشر العلني في يد الغريب**، لا موظّف مسجَّل الدخول داخل الحملة. وحاجز `authenticated` + `is_active` يغلق ذلك الخطر كاملاً. أمّا تضييق القراءة بين الموظفين فهو **نموذج أدوار** — وهو §٥.٣، قرار مؤجَّل صراحةً وغير محسوم.

ويلزمه توسعة صغيرة على `has_permission`: دالة أخت `is_active_employee()` تُرجع `true` للموظّف النشط ذي الملفّ. **لا تغيير في `has_permission` نفسها.**

### ⚠️ ٣.٢.١ حلٌّ انتقاليّ لا معماريةٌ نهائية — قرار صاحب المشروع

> **سياسة `select` الحالية على `passengers` انتقالية، ولا يجوز أن تصير المعمارية طويلة الأمد.**

**سببها الوحيد** أن التطبيق يجلب الحجاج **جلباً شاملاً عند الإقلاع** لكل مستخدم مهما كانت صلاحياته. لولا ذلك لأمكن أن تفرض RLS صلاحية القراءة أيضاً.

**Long-Term Architecture — خارج نطاق س٤:**

| # | المتطلَّب |
|---|---|
| ١ | **يجب أن يتوقّف التطبيق عن الجلب الشامل للحجاج عند الإقلاع.** |
| ٢ | المعمارية المستقبلية تنتقل إلى **جلب خاصّ بكل ميزة** (feature-specific loading). |
| ٣ | عندها **تُضيَّق سياسة `select`** لتفرض صلاحية القراءة كما تفرض صلاحية الكتابة اليوم. |

**هذه الإعادة التصميمية خارج س٤** ولا تُنفَّذ فيها. وهي مسجَّلة هنا لئلا يُقرأ التنازل الانتقالي يوماً على أنه القرار النهائي.

## ٣.٣ نمط السياسات — أربع صريحة لكل جدول

```sql
-- توضيحي — على passengers مثالاً
create policy passengers_select on public.passengers for select
  to authenticated using (public.is_active_employee());
create policy passengers_insert on public.passengers for insert
  to authenticated with check (public.has_permission('manage_passengers'));
create policy passengers_update on public.passengers for update
  to authenticated using (public.has_permission('manage_passengers'))
                    with check (public.has_permission('manage_passengers'));
create policy passengers_delete on public.passengers for delete
  to authenticated using (public.has_permission('manage_passengers'));
```

`to authenticated` صريح في كل سياسة: **لا تنطبق على `anon` إطلاقاً**.

| `buses` | `manage_buses` | |
| `camps` | `manage_camps` | منى وعرفة معاً |
| `rooms` | `manage_hotel` | |

## ٣.٥ سحب صلاحيات `anon`

```sql
-- توضيحي
revoke all on all tables in schema public from anon;
revoke all on all sequences in schema public from anon;
-- ثم تُعاد المنح المبرَّرة وحدها (§٤)
grant select on public.company_profile_public to anon;
grant select on public.company_assets to anon;
```

**وسحب `execute` عن الدوال غير المبرَّرة** — سبع دوال يستطيع `anon` تنفيذها اليوم بلا مبرّر:

```
active_season_id · announcement_audience · push_enabled_passengers
delete_empty_financial_group · create_financial_group_with_member
verify_user · create_user · update_user
```

> `create_user` و`update_user` مفتوحتان لـ`anon` **اليوم** — أي أن حامل المفتاح العلني يُنشئ مستخدماً بصلاحيات كاملة بلا مصادقة. هذه **C1**، وتُغلق نهائياً بحذفها في س٥ — لكن **سحب `execute` هنا يغلقها عملياً الآن**، وهو مكسب مجانيّ لا يوسّع النطاق.

## ٣.٦ تنبيهات البوابة — القرار ٢

`PilgrimPortal.tsx:137` يقرأ `announcements` مباشرةً بصفته `anon` في **المسار الاحتياطي** (حين لا بيانات حاج مخزَّنة). وهذا يخالف §٦.٢.

**المسار الأساسي سليم أصلاً:** `get_pilgrim_portal` تُرجع `announcements` ضمن إسقاطها المضبوط.

**الحل — نفس النمط المعتمد حرفياً:**

```
anon  →  get_portal_announcements()  →  SECURITY DEFINER  →  إسقاط مضبوط
```

```sql
-- توضيحي
create function public.get_portal_announcements() returns json
language sql stable security definer set search_path = public, pg_temp
as $$ select coalesce(json_agg(json_build_object(
       'id', a.id, 'body', a.body, 'priority', a.priority, 'show_at', a.show_at)
       order by (a.priority = 'عاجل') desc, a.show_at desc), '[]'::json)
     from public.announcements a
     where a.show_at <= now() and (a.expires_at is null or a.expires_at > now()); $$;
revoke execute on function public.get_portal_announcements() from public, authenticated;
grant execute on function public.get_portal_announcements() to anon, service_role;
```

**الإسقاط مطابق حرفياً** لما يقرأه العميل اليوم (`id, body, priority, show_at`) وبنفس الترشيح والترتيب — فلا تغيير سلوكيّ واحد. `expires_at` تُستعمل في الترشيح **ولا تخرج** — وهي اليوم تخرج ضمناً بمنح الجدول.

# ٤. Anonymous Access Inventory — جرد الوصول المجهول

> **قاعدة مُلزِمة:** أي وصول مجهول غير مذكور صراحةً في هذا الجرد **يُعدّ عيباً معمارياً**.

## ٤.١ ما يبقى بعد س٤ — مُبرَّر وموثَّق

| # | المورد | المبرّر التجاري | آلية الوصول | المالك |
|---|---|---|---|---|
| **ج١** | `company_profile_public` (عرض) | شاشة الدخول تعرض هوية الحملة قبل وجود أي جلسة — الاسم والشعار والألوان | `VIEW` بـ`security_invoker = false` · `grant select to anon` · **الأعمدة البنكية مستبعَدة من الإسقاط عمداً** | **ملفّ الشركة** — `ConfigProvider` · `companyService` |
| **ج٢** | `company_assets` (جدول) | شعار شاشة الدخول وخلفيتها وأيقونة الموقع | `grant select to anon` + سياسة تحصر القراءة في ستة مفاتيح: `logo · login_logo · login_background · favicon · portal_banner · dashboard_banner` | **ملفّ الشركة** — `companyService` |

| **ج٥** | `register_pilgrim_push(...)` | تفعيل الحاج للتنبيهات على جهازه | `SECURITY DEFINER` · يتحقّق من الوثيقة + الميلاد قبل التسجيل | **تنبيهات البوابة** — `PilgrimPortal` · عامل الخدمة |
| **ج٦** | `unregister_pilgrim_push(endpoint)` | إلغاء الحاج للتنبيهات | `SECURITY DEFINER` · يحذف بالـ`endpoint` وحده | **تنبيهات البوابة** — `PilgrimPortal` · عامل الخدمة |
| **ج٧** | `mark_pilgrim_notification_read(...)` | تعليم التنبيه مقروءاً | `SECURITY DEFINER` · يتحقّق من الوثيقة + الميلاد | **تنبيهات البوابة** — `PilgrimPortal` · عامل الخدمة |
| **ج٨** | `/auth/v1/token` (Supabase Auth) | تسجيل الدخول نفسه · وتأكيد كلمة المرور (س٣) | خدمة GoTrue — خارج مخطّط `public` · التسجيل الذاتي مُغلق (ن٤) | **نظام الهوية** — Supabase Auth · `LoginPage` · `confirmPassword` |

**ثمانية مداخل. لا تاسع.**

**المالك مسؤول عن:** تبرير بقاء المدخل عند كل مراجعة · ومراجعة أي تغيير يمسّ إسقاطه · وإضافة أي مدخل جديد إلى هذا الجرد قبل شحنه. و**صاحب المشروع هو المالك المُساءَل نهائياً** عن الجرد كله.

# ٧. Verification Plan

**§٩١–٩٥: الأمن يُثبَت بمحاولة الفعل الممنوع.**

## ٧.١ فحص القاعدة — بدور `anon` داخل `begin … rollback`

1. `select` على كل جدول من الأربعة عشر → **خطأ صلاحية أو صفر صف** — الأربعة عشر بلا استثناء
2. `insert` · `update` · `delete` على `passengers` → مرفوض
3. `verify_user` · `create_user` · `update_user` → **`permission denied`**
4. `get_pilgrim_portal` ببيانات صحيحة → يعمل
5. `get_portal_announcements()` → يعمل ويُرجع الحقول الأربعة **وحدها**
6. `company_profile_public` → يعمل · و`company_config` مباشرة → مرفوض
7. `company_assets` بمفتاح خارج الستة → صفر صف

## ٧.٢ فحص القاعدة — بدور `authenticated`

| المستخدم | المتوقّع |
|---|---|
| نشط بلا صلاحيات | يقرأ الجداول · **لا يكتب في شيء** |
| `manage_payments` وحدها | يقرأ الحجاج ✓ · يكتب الدفعات ✓ · **لا يكتب الحجاج** ✗ |
| **معطَّل** بكل الصلاحيات | **لا يقرأ ولا يكتب شيئاً** |
| بلا ملفّ | مثله |

## ٧.٣ فحص المتصفح

١٣ صفحة `NAV` بثلاث تركيبات صلاحيات (كامل · حسابات فقط · تقارير فقط) — صفر خطأ JS، ولا صفحة تُعرض فارغة بلا سبب.
وبوابة الحاج: الدخول · التنبيهات · التفعيل والإلغاء.

## ٧.٤ بوابة Advisors

المرجع **٢٤** بعد مزامنة النشر. المتوقّع **نقصان** (تختفي تنبيهات `anon_security_definer_function_executable` السبعة). **أي زيادة توقف الدمج.**

## ٧.٥ ما لا أستطيع تنفيذه — أصرّح به الآن

- الاستدعاء الحيّ عبر REST بمفتاح `anon` من خارج القاعدة — الشبكة محجوبة. الأوامر تُسلَّم جاهزة.
- **فحص المتصفح على النشر الحقيقي** — يتطلّب حساباً في `auth.users`، أي ن٣.

# ١٠. مستخدم «كسر الزجاج» — التعريف والمسار

**ما هو:** حساب في `auth.users` بملفّ في `user_profiles` يملك `manage_users` وكل الصلاحيات، **لا يُستعمل في العمل اليومي إطلاقاً**، ولا يُشارك أحد كلمة مروره.

**لماذا:** إن أخطأت سياسة فحُجب كل المستخدمين عن `user_profiles`، فلا سبيل لإصلاحها من داخل التطبيق. حساب كسر الزجاج هو المدخل الذي يبقى.

**كيف يُنشأ:** بنفس أداة الإقلاع الرسمية `seed_first_admin.mjs` ببريد ثانٍ — **لا آلية جديدة**.

**مسار الاستعادة الموثَّق** — يُكتب في `supabase/README.md`:

1. الدخول بحساب كسر الزجاج.
2. إن تعذّر: تشغيل migration التراجع (§٨) عبر لوحة Supabase أو `supabase db push`.
3. إن تعذّر ذلك أيضاً: مفتاح الخدمة يتجاوز RLS بالكامل — يُستعمل من الخادم وحده ولا يُطبع في أي سجلّ.

**ملاحظة مقصودة:** الخطوة ٣ ليست بديلاً عن ١ و٢، بل الطبقة الأخيرة. وذكرها صريحاً خير من اكتشافها وقت الأزمة.

# ٩.١ الدوال القديمة — Legacy Functions

> **قرار معتمد: `verify_user` و`create_user` و`update_user` تُترك معطّلة عمداً. لا تُصلَح.**

## الحالة المرصودة

الثلاث **معطّلة على الإنتاج** منذ ترحيل مزامنة النشر:

```
ERROR: function crypt(text, text) does not exist
CONTEXT: SQL function "verify_user" during startup
```

**السبب المباشر:** الترحيل ثبّت `search_path = public, pg_temp` على الثلاث (تصليب H5)، و`pgcrypto` مثبَّتة في مخطّط `extensions` — فلم يعد `crypt` و`gen_salt` مرئيَّين.

## لماذا لا تُصلَح — ثلاثة أسباب

| # | السبب |
|---|---|
| ١ | **خرجت من معمارية التشغيل.** لا مستدعي لها في المستودع: `verify_user` فقدت آخر مستدعٍ في س٣، و`create_user`/`update_user` في س٢ (`user-admin` حلّت محلّهما) |
| ٢ | **س٤ تسحب `execute` عنها** — فلا تُستدعى من الواجهة العامة أصلاً |
| ٣ | **س٥ تحذفها بالكامل** مع `public.users` |

**وسبب رابع أقوى:** إصلاحها يعيد لـ`create_user` قدرتها على إنشاء مستخدم بصلاحيات كاملة بلا مصادقة — وهي **C1** بعينها. تعطّلها اليوم يعمل في صالح النظام لا ضدّه.

> **لا يُنفَق جهد هندسي على ترميم مسارات مصادقة بائدة.**

**الأثر العملي: صفر.** مرصود وموثَّق، ولا يُعدّ عيباً مفتوحاً لأن معالجته المعتمدة هي الحذف في س٥.

# ٩.٢ Security Baseline Rules — قواعد الأساس الأمني

> **قواعد هندسية دائمة، لا تفاصيل تنفيذ لس٤.** تسري على كل ما يُبنى بعدها.

| # | القاعدة |
|---|---|
| **ق١** | **الجداول الجديدة لا ترث صلاحيات `anon` إطلاقاً.** الامتيازات الافتراضية في مخطّط `public` مسحوبة عن `anon` (`alter default privileges`)، وهذا **جزء دائم من الأساس الأمني** لا إجراء لمرة واحدة |
| **ق٢** | **كل Edge Function جديدة تستعمل طبقة `authorize()` المشتركة.** لا تكتب دالة منطق تفويض بنفسها، ولا تكرّر فحص الصلاحيات |
| **ق٣** | **كل مدخل مجهول جديد يُضاف إلى جرد الوصول المجهول قبل النشر.** الجرد هو **المصدر الوحيد للحقيقة** في المداخل المجهولة، وما ليس فيه عيبٌ معماري |
| **ق٤** | **الملفات المولَّدة (`database.ts`) لا تتلقّى تعديلاً يدوياً دائماً.** التعديل اليدوي مؤقّت فقط ويُسجَّل بـTODO لحظة إدخاله |

**ولا ميزة مستقبلية تتجاوز `authorize()` ولا تُدخل وصولاً مجهولاً مباشراً إلى جدول خارج الجرد.**
