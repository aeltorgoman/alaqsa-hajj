# ٣. Technical Design

## ٣.١ ما أثبتّه من قاعدة الإنتاج قبل التصميم

| الحقيقة | القيمة | لماذا تهمّ |
|---|---|---|
| عدد المستخدمين | **٦** | حجم البذر |
| أسماء مستخدمين متمايزة | **٦ من ٦** | لا تعارض على `UNIQUE` |
| **بريد لأي مستخدم** | **صفر** | `public.users` لا يحمل عمود بريد — انظر §٣.٦ |
| صيغة كلمات المرور | **٦ من ٦ بـ bcrypt** (`$2…`) | قابلة للنقل بلا إعادة تعيين |
| `auth.users` | **صفر** | أرض بكر — لا تعارض |

## ٣.٢ معرّف الدخول — Email مباشرةً

**لا اشتقاق ولا ترجمة ولا نطاق يُختار.** Security Architecture v1.2 §٤.١ ألغى Username كلياً: معرّف الدخول هو Email يُخزَّن في `auth.users.email` ويُستعمل كما هو في `signInWithPassword`.

البريد **لا يشترط أن يكون حقيقياً** — هو Login ID لا قناة اتصال (`admin@company.local` مثالاً).

**ما سقط من هذه الوثيقة بسقوط Username:** دالة الاشتقاق · قرار النطاق · فحص قبول GoTrue (خ١ سابقاً) · أي Mapping.

## ٣.٣ `user_profiles`

```
user_profiles
  id           uuid        PK · REFERENCES auth.users(id) ON DELETE CASCADE
  email        text        NOT NULL · UNIQUE   ← Login ID
  name         text        NOT NULL
  permissions  jsonb       NOT NULL DEFAULT '{}'
  is_active    boolean     NOT NULL DEFAULT true
  created_at   timestamptz DEFAULT now()
  updated_at   timestamptz DEFAULT now()
```

**`id` هو المفتاح الأجنبي الوحيد إلى `auth.users` في النظام كلّه — والثابت أ١٠ يمنع أي غيره.**

`email` هو Login ID، ويعكس `auth.users.email` كي تستطيع شاشة المستخدمين عرضه وقائمة المستخدمين البحث فيه بلا قراءة `auth.users` — وهو ما يمنعه الثابت أ١٠. `UNIQUE` يمنع ازدواج معرّف الدخول.

## ٣.٤ `has_permission()`

```sql
-- توضيحي
create function public.has_permission(p_key text) returns boolean
language sql stable security definer set search_path = public, pg_temp
as $$
  select coalesce(
    (select is_active and coalesce((permissions ->> p_key)::boolean, false)
       from public.user_profiles where id = (select auth.uid())),
    false);
$$;
```

**خصائص مقصودة:**

| الخاصية | السبب |
|---|---|
| `stable` | تُقيَّم مرة لكل عبارة لا لكل صفّ |
| `security definer` + `search_path` | تقرأ الجدول بلا حاجة لمنح المستخدم قراءةً مباشرة · ومحصّنة ضد تلاعب المسار |
| `(select auth.uid())` | يسمح للمخطّط بتخبئة القيمة |
| `coalesce(..., false)` مزدوج | **غياب الملفّ = صفر صلاحية** · **مفتاح غير موجود = صفر** · **`is_active=false` = صفر** |
| `execute` لـ `authenticated` فقط | `anon` لا يستدعيها؛ ولو استدعاها لعادت `false` (`auth.uid()` فارغ) |

**تنفّذ الثابتين أ٢ و أ٣ معاً:** الصلاحية من القاعدة، والتعطيل يسري على الطلب التالي بلا انتظار انتهاء الجلسة.

## ٣.٥ RLS على `user_profiles` — من لحظة الإنشاء

> **الدرس المستفاد من C2 مطبَّقاً:** `enable row level security` مع سياسة `using (true)` أسوأ من لا شيء — يبدو محمياً وهو مكشوف. الجدول الجديد يُولد بسياسات حقيقية.

| العملية | القاعدة |
|---|---|
| `select` | الملفّ الذاتي دائماً · وكل الملفّات لمن يملك `manage_users` |
| `insert` · `update` · `delete` | `manage_users` فقط |
| `anon` | **لا شيء** — لا منح ولا سياسة |

**هذا ليس تنفيذاً مبكراً لـ س٤.** س٤ تعالج الجداول **القائمة**. هذا الجدول يُنشأ الآن، وإنشاؤه مكشوفاً ثم إصلاحه لاحقاً = دين نخلقه عمداً، وهو ما يمنعه §84.

## ٣.٦ البذر — نقل المستخدمين الستة

**المسار:** `auth.admin.createUser({ email, password_hash, email_confirm: true })` بمفتاح الخدمة، ثم إدراج صفّ `user_profiles` بالمعرّف العائد.

**مصدر البريد:** `public.users` **لا يحمل عمود بريد**، و«اشتقاقه من اسم المستخدم» هو بالضبط ما ألغاه القرار الجديد. فالبريد **مُدخَل صريح** يُزوَّد به السكربت لكل مستخدم — إدخال بيانات لا ترجمة.

**نقل الـ hash لا إعادة تعيين:** التوثيق الرسمي ينصّ على دعم bcrypt و Argon2 في `password_hash`. والستة كلهم `$2…`. فيدخل كل مستخدم **بكلمة مروره الحالية نفسها** — والأهمّ أن هذا يُثبت الآلية عملياً قبل أن تُستعمل على بيانات حقيقية.

**لماذا سكربت لا Migration:** إنشاء مستخدم في `auth.users` يمرّ بـ GoTrue (صفوف `identities` وحقول داخلية). الإدراج المباشر بـ SQL غير مدعوم ويُنتج حسابات معطوبة. **والسابقة قائمة في المشروع:** `supabase/scripts/seed_test_seasons.sql` في م٢.٥.

**خصائص السكربت:**

- **يقرأ الاسم والصلاحيات وحالة التفعيل من `public.users` ديناميكياً** · **ويأخذ البريد من خريطة صريحة يزوّدها المشغّل**
- **Idempotent** — إعادة تشغيله تُحدِّث ولا تُكرِّر
- **حارس بنيوي** — يتوقّف إن وجد `auth.users` غير فارغ بما لا يطابق التوقّع (نمط `seed_test_seasons.sql`)
- **لا يُشغَّل تلقائياً** — يُنفَّذ يدوياً بمفتاح الخدمة

## ٣.٧ التعايش — النظامان معاً

```
اليوم وحتى س٢:
  الدخول    →  verify_user  →  public.users        ← المسار الحيّ
  الجديد    →  auth.users   →  user_profiles       ← مبنيّ وغير مستهلَك
```

`public.users` **يبقى مصدر الحقيقة** حتى س٢. لا محفّز مزامنة ولا نسخ تلقائي — إضافة المزامنة تعني منطقاً مؤقّتاً يُحذف بعد أسبوع، وهو تعقيد بلا مقابل.

**النتيجة: نافذة انحراف** — تعديل مستخدم في التطبيق بين س١ و س٢ لا ينعكس على `user_profiles`.

## ٣.٧.١ TR‑1 — قاعدة تحويل مُلزِمة

> ### **TR‑1 — Transition Rule**
>
> **During the transition window between S1 completion and S2 completion, creating users, deleting users, or modifying permissions is prohibited.**
>
> **خلال نافذة التحويل الممتدّة من اكتمال س١ إلى اكتمال س٢، يُمنع إنشاء مستخدم أو حذف مستخدم أو تعديل أي صلاحية.**

**هذه قاعدة تشغيلية مُلزِمة، لا توصية ولا تخفيف مخاطرة.** مرتبتها مرتبة قواعد التشغيل ت١–ت٧ في معمارية المواسم: لا تغيّر التصميم، وتحكم **متى** يُستعمل ما بُني.

| | |
|---|---|
| **تبدأ** | لحظة اكتمال س١ (دمج PR٢ وتشغيل السكربت بنجاح) |
| **تنتهي** | **تلقائياً** لحظة اكتمال س٢ — بلا قرار ولا إجراء إضافي |
| **ما تمنعه** | إنشاء مستخدم · حذف مستخدم · تعديل صلاحيات · تعطيل أو تفعيل حساب |
| **ما لا تمنعه** | كل عمليات النظام الأخرى — الحجاج · الباصات · المخيمات · الفندق · الطيران · الحسابات · التقارير · المواسم · البوابة |
| **نطاقها** | إدارة المستخدمين وحدها |

**السبب:** `public.users` و`user_profiles` مصدران متوازيان في هذه النافذة بلا مزامنة (§٣.٧). أي تعديل على أحدهما يُنتج انحرافاً صامتاً ينتقل إلى س٢ فيصير خطأ تفويض حقيقي — مستخدم يملك في نظام ما لا يملكه في الآخر.

**التنفيذ:** قاعدة تشغيلية على المشغّل، لا حارس في الشيفرة. إضافة حارس مؤقّت يُحذف بعد أسبوع تعقيد بلا مقابل (§٣.٧)، ومخالف لـ §84.

**شبكة الأمان إن خُرقت:** السكربت Idempotent وSelf-Healing (فحصا ٢١ و٢٣)، فإعادة تشغيله قبل س٢ تُصلح الانحراف. **لكن هذا علاج لا رخصة** — الخرق يوجب إعادة التشغيل وإعادة فحوص §٧.٤ قبل بدء س٢.

## ٣.٨ ملاحظة مسجَّلة — لا توقف المرحلة

**القاعدة تحوي ٢١ مفتاح صلاحية، والشيفرة تعرّف ١١.**

عشرة مفاتيح قديمة في بيانات المستخدمين لا وجود لها في `ALL_PERMISSIONS`:
`add_passenger` · `delete_passenger` · `edit_passenger` · `export_reports` · `print_reports` · `view_buses` · `view_camps` · `view_hotel` · `view_passengers` · `view_users`

**القرار: تُنقل كما هي.** `has_permission()` لا تُستدعى إلا بالمفاتيح الأحد عشر، فالعشرة خاملة تماماً. تنظيفها قرار سلوكيّ يحتاج اعتماداً مستقلاً، ولا مبرّر لإقحامه في س١.

**مسجَّلة للمراجعة الشاملة.**

## صفر ملف داخل `src/`

**هذا معيار مراجعة صريح.** أي ملف في `src/` يظهر في diff س١ = خرق للنطاق.

### `src/types/database.ts` — لا يُعاد توليده في س١

الجدول الجديد سيظهر في الأنواع المولَّدة، لكن **لا شيء في التطبيق يستعمله قبل س٢**. وإعادة التوليد الآن:

- تُدخل تغييراً في `src/` يخالف قيد «بلا تغيير في التطبيق»
- تُنتج نوعاً ميتاً لا مستهلك له

**القرار: يُعاد التوليد في س٢** حين يستعمله الدخول أول مرة. مسجَّل كي لا يُنسى.

# ٥. Database Changes

## ٥.١ ما يُضاف

| النوع | الاسم |
|---|---|
| جدول | `public.user_profiles` |
| قيود | `PK(id)` · `FK(id) → auth.users(id) ON DELETE CASCADE` · `UNIQUE(username)` |
| دالة | `public.has_permission(text)` — `SECURITY DEFINER` · `STABLE` · `search_path` مثبّت |
| سياسات | ٤ على `user_profiles` |
| منح | `execute` على `has_permission` لـ `authenticated` |
| صفوف | ٦ في `user_profiles` + ٦ في `auth.users` (بالسكربت) |

## ٥.٢ ما لا يُمسّ — صراحةً

**لا `alter` ولا `drop` ولا `revoke` على أي كائن قائم.**

`public.users` · `verify_user` · `create_user` · `update_user` · سياسات الجداول القائمة · منح `anon` · محفّزات الموسم · `close_season` · `delete_season` — **كلها كما هي حرفياً.**

## ٥.٣ المنح على الجدول الجديد

| الدور | الصلاحية |
|---|---|
| `anon` | **لا شيء** |
| `authenticated` | `select` · `insert` · `update` · `delete` — **مقيَّدة كلها بـ RLS** |
| `service_role` | كاملة (يحتاجها السكربت) |

> ⚠️ **الامتيازات الافتراضية في مخطّط `public` قد تمنح الجدول الجديد لـ `anon` تلقائياً.** الترحيل يجب أن يتضمّن `revoke` صريحاً لا أن يفترض النظافة. **بند مراجعة إلزامي.**

## ٥.٤ التوافق مع Migrations القائمة

الترحيل **إضافي بحت** ولا يلمس أي كائن سابق، فلا تعارض مع الترحيلات الثمانية القائمة ولا مع ثوابت المواسم ث١–ث٦.

### فحص ٢٣ — Self-Healing بالتفصيل

**Idempotency تُثبت أن إعادة التشغيل لا تُفسد. Self-Healing تُثبت أنها تُصلح.** وهما خاصيّتان مختلفتان، والثانية هي ما يجعل السكربت شبكة أمان حقيقية لـ TR‑1.

| الخطوة | الفعل | النتيجة المطلوبة |
|---|---|---|
| ٢٣.١ | حذف **مستخدم واحد** من `auth.users` | `auth.users` = ٥ · و`user_profiles` = ٥ (بـ `ON DELETE CASCADE`) |
| ٢٣.٢ | إعادة تشغيل السكربت | ينتهي بنجاح بلا خطأ |
| ٢٣.٣ | فحص العدد | `auth.users` = **٦** · `user_profiles` = **٦** |
| ٢٣.٤ | فحص الهوية | **المحذوف وحده أُعيد إنشاؤه** · الخمسة الباقون بمعرّفاتهم (`id`) الأصلية **بلا تغيير** · صفر تكرار في `username` |

**الشرط الحاسم في ٢٣.٤:** معرّفات الخمسة السليمين **يجب ألّا تتغيّر**. لو أعاد السكربت إنشاءهم لصارت `user_profiles.id` جديدة، ولانقطعت كل إشارة مستقبلية إليها. السكربت يُصلح الناقص ولا يمسّ القائم.

**ملاحظة على المستخدم المُعاد:** سيحمل `id` جديداً حتماً — لأن الحساب حُذف فعلاً. هذا متوقّع ومقبول في س١ لأن لا شيء يشير إلى `user_profiles.id` بعد. **يصير غير مقبول بعد س٤** حين تعتمد السياسات عليه، ولذلك TR‑1 تمنع الحذف أصلاً.

## ٧.٥ Dry Run — إلزاميّ قبل التشغيل على البيئة المستهدفة

> **لا يُشغَّل سكربت البذر على البيئة المستهدفة قبل Dry Run موثَّق.**

**التسلسل الملزم:** `PR٢ → Review → Approval → Dry Run → Verification → Production Run`

### ما هو Dry Run هنا

تشغيل السكربت بوضع **يقرأ ولا يكتب** (`--dry-run`): يقرأ `public.users`، ويشتقّ البريد لكل مستخدم، ويقارن بحالة `auth.users` و`user_profiles` الراهنة، ثم **يطبع خطّة التنفيذ ويخرج بلا أي كتابة**.

**هذا شرط تصميميّ على السكربت:** وضع Dry Run جزء من متطلّباته في PR٢، لا إضافة لاحقة.

### ما يجب أن يُظهره التقرير

| # | البند | المتوقّع قبل أول تشغيل |
|---|---|---|
| ١ | عدد المستخدمين المقروءين من `public.users` | ٦ |
| ٢ | البريد المشتقّ لكل مستخدم | ٦ · متمايزة · بالنطاق المعتمد |
| ٣ | **سيُنشأ** | ٦ |
| ٤ | **سيُحدَّث** | ٠ |
| ٥ | **سيُترك بلا تغيير** | ٠ |
| ٦ | **صفر عملية حذف** — في كل الأحوال | ✓ |
| ٧ | تحذيرات: اسم مكرّر · hash غير صالح · تعارض بريد | لا شيء |

### بوابة القبول

**التقرير يُراجَع ويُعتمد قبل التشغيل الفعلي.** أي تباين بينه وبين المتوقّع يوقف التشغيل ويعود إلى المراجعة.

**وبعد التشغيل الفعلي:** يُعاد Dry Run مرة أخرى، ويجب أن يُظهر **٦ بلا تغيير · صفر إنشاء · صفر تحديث** — وهو إثبات مستقلّ للـ Idempotency (فحص ٢١) بلا كتابة.

### التوثيق

مخرجات Dry Run (قبل وبعد) تُرفق في PR٢ كدليل تحقّق، لا تُلخَّص.

---

> **حدّ معروف مسبقاً:** الفحوص ١٧–٢٣ و٧.٥ كلها تتطلّب تشغيل السكربت بمفتاح الخدمة واتصالاً حيّاً بالمشروع، والشبكة من بيئة التنفيذ محجوبة بسياسة تنظيمية (`CONNECT tunnel failed, 403`). **فالتشغيل — Dry Run والفعليّ معاً — بيد المالك، وأنا أراجع مخرجاته وأتحقّق ممّا يمكن التحقّق منه عبر SQL** (الأعداد · الروابط · التطابق). وما يتطلّب مصادقة حيّة (١٠ · ٢٢) **سأصرّح بأنه غير مُنفَّذ** ولن أدّعي خلاف ذلك — كما في س٠.

# ٨. Rollback Plan

**س١ أسهل مرحلة في الخارطة للتراجع، لأن لا شيء يستهلك مخرجاتها.**

| الخطوة | الفعل |
|---|---|
| ١ | حذف الحسابات الستة من `auth.users` (سكربت عكسي) — الحذف يُسقط صفوف `user_profiles` بـ `ON DELETE CASCADE` |
| ٢ | **`drop table public.user_profiles`** — يُسقط السياسات الأربع معه |
| ٣ | **`drop function public.has_permission(text)`** |
| ٤ | `git revert` للـ PRs |

> ### ⚠️ الترتيب مُلزِم — أثبته التنفيذ
>
> **الجدول قبل الدالة، لا العكس.** السياسات الأربع تعتمد على `has_permission()`، فمحاولة حذف الدالة أولاً تفشل:
>
> ```
> ERROR: cannot drop function has_permission(text) because other objects depend on it
> ```
>
> وحذف الجدول يُسقط سياساته معه، فتتحرّر الدالة. **الترتيب المصحَّح مُختبَر: الجدول = `0` · الدالة = `0`.**
>
> رُصد أثناء تنفيذ PR١ (#60) وصُحّح هنا في v1.1-patch1.

**زمن التراجع: دقائق.**

**أثر التراجع على التطبيق: صفر** — لأن التطبيق لم يكن يستعمل شيئاً منها أصلاً. وهذه بالضبط فائدة قيد «بلا تغيير في التطبيق».

**نقطة اللاعودة:** ليست في س١. تبدأ في **س٤** حين تُسحب صلاحيات `anon`.
