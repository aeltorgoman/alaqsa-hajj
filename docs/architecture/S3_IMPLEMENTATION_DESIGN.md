# ١. Scope

## ما تشمله س٣

| # | البند | المرجع |
|---|---|---|
| ١ | `season-admin` تنتقل من `verify_user(username,password)` إلى **JWT + النمط الثلاثي** | §٧.١ |
| ٢ | `Scan-passport` تكتسب النمط الثلاثي + `manage_passengers` | §٧.٣ |
| ٣ | `send-pilgrim-push` تكتسب النمط الثلاثي + `manage_portal` | §٧.٤ |
| ٤ | مصدر `Scan-passport` و`send-pilgrim-push` **ينتقل إلى المستودع** — شرط لازم لتعديلهما | §١٤ (نُقل من س٩) |
| ٥ | مستهلكا `season-admin` يتوقّفان عن إرسال كلمة المرور عبر الشبكة | §٧.١ |

**النتيجة النهائية للمرحلة:** لا تبقى Edge Function واحدة تُنفَّذ لمن يحمل مفتاح `anon` وحده. و`verify_user` تفقد **آخر مستدعٍ لها في الشيفرة**، فيصير حذفها في س٥ حذفَ ميت لا كسرَ حيّ.

## ما لا تشمله — صراحةً

| البند | مكانه |
|---|---|
| حدّ معدّل · تصفية استجابة `Scan-passport` · حصر CORS | س٩ |
| `audit_log` | س٨ |
| سياسات RLS على الجداول التشغيلية · سحب صلاحيات `anon` | س٤ |
| حذف `verify_user` · `create_user` · `update_user` · `public.users` | س٥ |
| البوابة والتخزين | س٦ · س٧ |
| نموذج الأدوار (§٥.٣) | قرار مستقل غير محسوم |
| أي تغيير في تجربة المستخدم أو تصميم الشاشات | خارج المرحلة |

**لا Refactoring، ولا معالجة دَين تقني، ولا توسيع نطاق.**

# ٢. Business Impact

| ما يراه المستخدم | قبل | بعد |
|---|---|---|
| إقفال موسم / حذف موسم | يعيد إدخال كلمة المرور → تُرسل إلى دالتنا | **يعيد إدخال كلمة المرور كما هي** → تُرسل إلى Supabase Auth وحده، لا إلى دالتنا |
| مسح جواز/هوية | يعمل لأي حامل مفتاح | يعمل لمن سجّل دخوله ويملك `manage_passengers` |
| إرسال تنبيه للحجاج | يعمل لأي حامل مفتاح | يعمل لمن سجّل دخوله ويملك `manage_portal` |

**لا تغيير مرئيّ واحد لمستخدم مخوَّل.** الصفحات الثلاث محجوبة أصلاً خلف الصلاحيات نفسها في `NAV`، فمن يصل إلى الزرّ يملك الصلاحية بالضرورة.

**قيد نشر يجب ألّا يُخفى:** حتى تُنفَّذ ن٣ (`seed_first_admin`) لا يوجد حساب في `auth.users`، فلا أحد يسجّل دخوله، فالدوال الثلاث ترفض الجميع. هذا **قيد نشر قائم أصلاً بعد س٢** ولا تُحدثه س٣.

## ٣.١ الحالة القائمة — مُتحقَّق منها من الشيفرة والإنتاج

|---|---|---|---|---|---|

| `Scan-passport` | 18 | ✅ `true` | **لا شيء** | **لا شيء** | ❌ |
| `send-pilgrim-push` | 1 | ✅ `true` | **لا شيء** | **لا شيء** | ❌ |

send-pilgrim-push   PortalPage.tsx:204

## ٣.٢ الحارس المشترك — النمط الثلاثي في موضع واحد

`supabase/functions/_shared/authorize.ts` — دالة واحدة تستعملها الدوال الثلاث:

```ts
// توضيحي
export async function authorize(req: Request, permission: string) {
  const url = Deno.env.get("SUPABASE_URL")!;
  const token = (req.headers.get("Authorization") ?? "").replace(/^Bearer\s+/i, "");
  if (!token) return { error: fail(401, "غير مصرّح.") };

  // (٢) الهوية — يمنع مفتاح anon، وهو JWT صالح يجتاز verify_jwt
  const admin = createClient(url, Deno.env.get("SUPABASE_SERVICE_ROLE_KEY")!,
                             { auth: { persistSession: false } });
  const { data: caller } = await admin.auth.getUser(token);
  if (!caller?.user) return { error: fail(401, "غير مصرّح.") };

  // (٣) الصلاحية — has_permission بهوية المستدعي نفسه
  const asUser = createClient(url, Deno.env.get("SUPABASE_ANON_KEY")!, {
    global: { headers: { Authorization: `Bearer ${token}` } },
    auth: { persistSession: false },
  });
  const { data: allowed } = await asUser.rpc("has_permission", { p_key: permission });
  if (allowed !== true) return { error: fail(403, "لا تملك الصلاحية المطلوبة.") };

  return { admin, userId: caller.user.id };
}
```

و(١) هو `verify_jwt = true` على الدوال الثلاث. **الثلاثة معاً — §٧.٢.**

**لماذا `has_permission` عبر عميل بهوية المستخدم لا قراءة مباشرة للجدول؟** §٥.٢: «كل قرار تفويض في النظام يمرّ من هنا. لا فحص صلاحية في أي مكان آخر». عميل بمفتاح الخدمة يجعل `auth.uid()` فارغاً فتُرجع الدالة `false` دائماً — لذلك يلزم عميل بهوية المستدعي.

**مُتحقَّق من التوثيق الرسمي** (`guides/functions/secrets` و`guides/functions/auth-legacy-jwt`): `SUPABASE_ANON_KEY` ما زال ضمن الأسرار الافتراضية للدوال، ونمط «عميل بترويسة المستخدم» هو النمط الموثَّق حرفياً.

## ٣.٣ `season-admin` — الشكل الجديد

| | قبل | بعد |
|---|---|---|
| جسم الطلب | `{action, username, password, …}` | `{action, …}` — **بلا اعتماد** |
| الهوية | `verify_user` | `authorize(req, "view_archive")` |
| اسم الإيصال (`closed_by`) | من صفّ `public.users` | من `user_profiles.name` بمعرّف الجلسة |
| `verify_jwt` | `false` | **`true`** |

العمل `verify` يبقى كما هو دوراً ومعنى: يُثبت الهوية والصلاحية ويعيد الاسم، **بلا تنفيذ ولا تغيير**. و`close_season`/`delete_season` تُستدعيان بمفتاح الخدمة كما هما (محجوبتان عن `anon` و`authenticated` منذ م١) — **لا تغيير في القاعدة**.

## ٣.٤ تأكيد كلمة المرور — يبقى، ولا يُرسَل إلى دالتنا

§٧.١ حرفياً: «إعادة إدخال كلمة المرور تبقى — كتأكيد لعملية لا رجعة فيها، لا كآلية أمنية»، و«كلمة المرور: **لا تُرسل**».

**التنفيذ المقترح — عميل تأكيد منفصل في المتصفح:**

```ts
// توضيحي — src/season/confirmPassword.ts
const confirmClient = createClient(URL, ANON, {
  auth: { persistSession: false, autoRefreshToken: false, detectSessionInUrl: false },
});
const { error } = await confirmClient.auth.signInWithPassword({ email, password });
return !error;
```

كلمة المرور تذهب إلى نقطة `‎/auth/v1/token` وحدها — الجهة التي تملك التحقّق منها — ولا تمرّ بدالتنا ولا بسجلّاتها. والعميل المنفصل (`persistSession: false`) **لا يمسّ الجلسة القائمة**، فلا استبدال رمز ولا `onAuthStateChange` في منتصف المعالج.

## ٣.٥ ما يبقى كما هو — عمداً

- خطوات المعالج الخمس وترتيبها ونصوصها.
- `close_season` · `delete_season` · محفّزات الموسم · قاعدة ت١.
- `user-admin` — لا تُمسّ في هذه المرحلة (انظر §١٠).
- منطق `Scan-passport` و`send-pilgrim-push` الداخلي: **لا سطر واحد يتغيّر منه**؛ يُضاف الحارس في أعلى المعالج فقط.

# ٥. Database Changes

**لا شيء. صفر migration.**

`has_permission()` موجودة منذ س١ ومُختبَرة (٨ من ٨). امتياز `execute` عليها ممنوح لـ PUBLIC بالافتراض، فدور `authenticated` يستدعيها بلا منح إضافي. **إن ثبت خلاف ذلك عند التحقّق، يُضاف `grant execute … to authenticated` في ترحيل واحد — وأصرّح به قبل التنفيذ لا بعده.**

# ٦. Risks

| # | الخطر | التخفيف |
|---|---|---|
| **خ١** | ترتيب النشر يوقف إدارة المواسم | الدالة الجديدة **متوافقة رجعياً**: تتجاهل الحقلين الزائدين وتعتمد على JWT الذي يرسله `functions.invoke` أصلاً بعد س٢. لذلك: **الدالة أولاً، ثم العميل** — بلا نافذة تعطّل |
| **خ٢** | بين نشر الدالة ودمج العميل يمرّ التأكيد بأي كلمة مرور | نافذة دقائق · التأكيد ليس ضابطاً أمنياً (§٧.١) · وت١ تمنع أي إقفال حقيقي قبل م٧. **مصرَّح به لا مسكوت عنه** |
| **خ٣** | كسر مسح الجوازات — مسار حقيقي بفاتورة حقيقية | الحارس يُضاف في أعلى المعالج بلا مسّ المنطق · فحص متصفح على المسار الحيّ `PassengersPage ← scanDocument` قبل الدمج · التراجع = إعادة نشر النسخة السابقة (دقيقة) |
| **خ٤** | تعديل دالة مصدرها من الإنتاج لا من المستودع | **commit أول يُدخل المصدر كما هو حرفياً**، والتعديل في commit ثانٍ — فيصير الفرق مقروءاً في المراجعة سطراً بسطر |
| **خ٥** | `_shared/` لا يُرفع مع حزمة الدالة عند النشر | يُتحقَّق منه **قبل** كتابة الشيفرة النهائية بنشر تجريبي لدالة واحدة؛ إن تعذّر، يُكرَّر الحارس في الدوال الثلاث (٢٠ سطراً × ٣) ويُسجَّل السبب |
| **خ٦** | `has_permission` تُرجع `false` لسبب بيئي (مفتاح مفقود) فتُغلق الدوال الثلاث | الحارس يميّز 401 عن 403 · فحص قاعدة قبل النشر · التراجع لكل دالة مستقل |

# ٧. Verification Plan

## ٧.١ ما لا أستطيع تنفيذه — أصرّح به قبل البدء

الشبكة من بيئة التنفيذ محجوبة عن `*.supabase.co` بسياسة تنظيمية (`CONNECT tunnel failed, 403`). لذلك **الاختبار الحيّ الوارد في §١٥ لس٣ — «استدعاء `season-admin` بمفتاح anon → رفض» — لا أستطيع تنفيذه**، وأسلّمه أمراً جاهزاً للتشغيل عندك. لن أدّعي تنفيذه.

## ٧.٢ فحص قاعدة البيانات — عبر MCP، داخل `begin … rollback`

1. `has_permission('view_archive')` بهوية مستخدم يملكها → `true`
2. بهوية مستخدم لا يملكها → `false`
3. بمستخدم **معطَّل** يملكها → `false`
4. بهوية بلا ملفّ → `false`
5. `anon` → `false`
6. إثبات أن `execute` متاح لدور `authenticated`

## ٧.٣ فحص المتصفح — بمحاكاة Supabase Auth

| # | الفحص | المتوقّع |
|---|---|---|
| ١ | مسح جواز بمستخدم يملك `manage_passengers` | الحقول الخمسة تُملأ |
| ٢ | رفض 403 من `Scan-passport` | رسالة واضحة بلا انهيار |
| ٣ | معالج الإقفال: كلمة مرور خاطئة | يقف عند الخطوة ١ برسالة |
| ٤ | كلمة مرور صحيحة | يتقدّم · **الجسم بلا `username` ولا `password`** |
| ٥ | حوار الحذف | مثله |
| ٦ | الجلسة القائمة لا تتبدّل بعد التأكيد | نفس `access_token` قبل وبعد |
| ٧ | ١٣ صفحة `NAV` | صفر خطأ JS |

## ٧.٤ الفحص الأمني الحيّ — أوامر تُشغَّل عندك بعد النشر

```bash
# ١) بمفتاح anon وحده → يجب 401
curl -s -o /dev/null -w "%{http_code}\n" -X POST \
  "$SUPABASE_URL/functions/v1/season-admin" \
  -H "Authorization: Bearer $ANON_KEY" -H "Content-Type: application/json" \
  -d '{"action":"verify"}'

# ٢) بلا ترويسة → يجب 401
# ٣) برمز مستخدم لا يملك view_archive → يجب 403
# ٤) برمز مستخدم يملكها → يجب 200
```

**معيار النجاح: ٤٠١ · ٤٠١ · ٤٠٣ · ٢٠٠.** أي `200` في الأول أو الثاني = المرحلة فاشلة ويُتراجع عنها فوراً.

## ٧.٥ فحص عدم الانحدار

`npm run build` · `npm run lint` بلا زيادة عن المرجع (٢٩١) · `get_advisors(security)` لا يزيد عدده.

# ١٠. ملاحظة مسجَّلة — `user-admin` و§٥.٢

`user-admin` (س٢، منشورة) تقرأ `is_active` و`permissions` من `user_profiles` مباشرة بدل استدعاء `has_permission()`. **المنطق مطابق والسلوك واحد**، لكن §٥.٢ تنصّ على أن التفويض يمرّ من نقطة واحدة.

**ليست عيباً في الشيفرة ولا ثغرة** — فلا أعيد فتح س٢ من تلقائي. مواءمتها تكلّف ثلاثة أسطر داخل PR ١ إن أردت (§١٢، القرار ٢).

---

# ١١. أثر جانبيّ مقصود — `verify_user` تفقد آخر مستدعٍ

بعد PR ١ لا يبقى في المستودع كلّه استدعاء واحد لـ `verify_user` (الجرد في §٣.١ كامل). فحذفها في س٥ يصير **حذف شيفرة ميتة**، لا كسر مسار حيّ. هذا يخفّض خطر س٥ قبل الوصول إليها.
