| # | البند |
|---|---|

# ٢. Business Impact

| | |
|---|---|
| **الأثر على المستخدم** | **ظاهر لأول مرة**: حقل «اسم المستخدم» يصير «البريد (Login ID)» |
| **الأثر على الجلسة** | جلسة بانتهاء صلاحية وتجديد بدل جلسة تنتهي بإغلاق التبويب |
| **ما يُغلق** | **H1** (الـ hash يعبر الشبكة) · **H2** (التعطيل لا يمنع الدخول) · جزء من **H3** |

**أول مرحلة يلمسها المستخدم.** ولذلك فحص المتصفح فيها ليس تكميلياً بل مركز التحقّق.

# ٣. Technical Design

## ٣.١ الحالة القائمة — مُتحقَّق منها من الشيفرة

| الحقيقة | القيمة |
|---|---|
| ملفات تستهلك `currentUser` | **١٣** |
| مواضع `hajj_user` في `sessionStorage` | ٣ — كلها في `App.tsx` |
| `currentUser.username` كـ `created_by` | **٤** في `FinancePage` |
| `currentUser.username` مُرسَل إلى `season-admin` | **٢** في `SeasonCloseWizard` + `SeasonDeleteDialog` |
| نوع `User` الحالي | `id: number` · `username` · `password` · `permissions` · `is_active?` |

## ٣.٢ مسار الدخول الجديد

```
اليوم                                    بعد س٢
─────                                    ──────
rpc("verify_user", {username, password})  signInWithPassword({ email, password })
      ↓ صفّ فيه hash كلمة المرور                ↓ جلسة JWT
sessionStorage["hajj_user"]                supabase.auth.getSession()
      ↓                                          ↓
currentUser.permissions                     user_profiles عبر auth.uid()
```

**كلمة المرور لا تغادر نموذج الدخول، ولا hash يعبر الشبكة.**

## ٣.٣ نوع `User` — التحوّل

| الحقل | اليوم | بعد س٢ |
|---|---|---|
| `id` | `number` | **`string` (uuid)** |
| `username` | `string` | **`email: string`** |
| `password` | `string` | **يُحذف** |
| `permissions` | `Record<string, boolean>` | كما هو — من `user_profiles` |
| `is_active` | `boolean \| null` | كما هو |

> ⚠️ **`id: number → string` هو أوسع أثر تقني في س٢.** ١٣ ملفاً تستهلك `currentUser`، وأي مقارنة `===` مع رقم تنكسر صامتة. جرد كل موضع شرطُ قبول (§٧).

## ٣.٤ استرجاع الجلسة

```
getSession()  →  إن وُجدت: اقرأ user_profiles بـ auth.uid()
              →  إن لم تُوجد أو لا ملفّ لها: اعرض شاشة الدخول
onAuthStateChange  →  الخروج من تبويب آخر ينعكس فوراً
```

**«جلسة بلا ملفّ» = لا دخول.** تطبيق مباشر لـ §٤.٣: الوجود في `auth.users` لا يمنح شيئاً.

## ٣.٥ ما يبقى كما هو — عمداً

`public.users` · `verify_user` · `create_user` · `update_user` — **قائمة بلا تغيير حتى س٥**. حذفها هنا يقطع التراجع.

# ٩. `season-admin` — أثر مؤجَّل بقرار

الدالة تتوقّع `{ username, password }` وتتحقّق عبر `verify_user` من `public.users`. بعد س٢ سيصلها **بريد** لا اسم مستخدم، فتفشل.

**الأثر العملي: صفر.** قاعدة التشغيل **ت١** تمنع أي إقفال أو حذف موسم حقيقي قبل اكتمال م٧. والدالة تنتقل إلى JWT في **س٣** بحسب §١٤.

**القرار: يُترك كما هو، ويُوثَّق أن إقفال/حذف الموسم غير متاح بين س٢ وس٣.**

# ١٠. إدارة المستخدمين — الخيار (أ) معتمد

**المشكلة التي حُسمت:** `UsersPage` تنشئ عبر `create_user` في `public.users`. بعد س٢ يصير الدخول من `auth.users`، فأي حساب يُنشأ من الشاشة **لا يستطيع الدخول** — صامتاً.

## القرار المعتمد

> **إدارة المستخدمين جزء من س٢، لا تنظيفاً لاحقاً.**
> **`create_user` يُستبدَل بتنفيذ خادميّ آمن الآن.**

| # | المتطلَّب المُلزِم |
|---|---|
| ١ | **كل مستخدم جديد يُنشأ في `auth.users`** |
| ٢ | **كل مستخدم له صفّ مقابل في `user_profiles`** |
| ٣ | **الصلاحيات تبقى في `user_profiles`** |
| ٤ | **`has_permission()` تبقى نقطة التفويض الوحيدة** |
| ٥ | **لا نظامَي هوية متوازيين** |
| ٦ | **لا طبقة توافق مؤقّتة** |
| ٧ | **لا مصادقة قديمة** |

**`UsersPage` تنتهي س٢ وهي متوافقة مع المعمارية النهائية** — لا مرحلة لاحقة تُصلحها.

## التنفيذ — Edge Function `user-admin`

| العمل | ما يفعله |
|---|---|
| `create` | `auth.admin.createUser({ email, password, email_confirm: true })` ثم صفّ `user_profiles` — **في مسار واحد** |
| `update` | تعديل البريد أو كلمة المرور في `auth.users` · والاسم والصلاحيات وحالة التفعيل في `user_profiles` |
| `delete` | حذف من `auth.users` — الصفّ يسقط بـ `ON DELETE CASCADE` |

**النمط الثلاثي المُلزِم (Security Architecture v1.2 §٧.٢) — الثلاثة معاً:**

```
verify_jwt = true          ← يمنع الطلبات بلا ترويسة
getUser(jwt) داخل الدالة   ← يمنع مفتاح anon
has_permission('manage_users')  ← يمنع غير المخوّل
```

**ولا يُقرأ `manage_users` مما يرسله المتصفح** — يُقرأ من `user_profiles` على الخادم.

### حرّاس مُلزِمة

- **لا يُنشئ حساباً بلا ملفّ** — فشل إنشاء الملفّ يوجب حذف الحساب المُنشأ (لا يبقى حساب يتيم يخالف المتطلَّب ٢).
- **المستخدم لا يسحب `manage_users` من نفسه** — الحارس القائم في `UsersPage` يُنقل إلى الخادم.
- **المستخدم لا يعطّل نفسه ولا يحذف نفسه.**

### أثره على `create_user` / `update_user`

**لا تُستدعيان من الواجهة بعد س٢ إطلاقاً.** حذفهما من القاعدة يبقى في **س٥** — لأن حذفهما هنا يقطع مسار التراجع (§٨)، لا لأن الواجهة تحتاجهما.
